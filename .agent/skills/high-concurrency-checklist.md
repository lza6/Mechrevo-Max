# Skill: "高并发/高可用"检查（本项目定义）

## 适用场景
任何涉及 EC 访问频率、轮询、并发调用的改动。

## 前置读取
`docs/SPEC.md` §7（本项目的"高并发"= EC 访问竞争，不是 QPS）、§5.1（限速红线）。

## 本项目不存在的东西（不要硬塞）
QPS / 连接池 / 多租户 / 限流中间件 / 熔断器 / Redis / Kafka / 分片 / CDN / 容器化 —— 单机单用户桌面应用，这些场景不存在。

## 真正的等价检查项
| 真实风险 | 检查方式 |
|---|---|
| EC 设备中途消失（驱动卸载/休眠） | 每次访问失败能否被捕获并提示、不 panic；`probe()` 可用 |
| 多线程同时访问 EC | `AppState.ec` 互斥覆盖所有命令；`lock_ec_serializes_access` 单测 |
| 轮询与用户操作冲突 | 忙时暂停轮询；`refresh` 在飞标记；滑块编辑锁 |
| 访问频率过高导致 EC 停摆 | `AccessThrottle` 在唯一 IOCTL 出口；默认 50 次/秒，硬下限 100 次/秒 |
| 极端值输入损坏硬件 | `PowerLimits::new` 范围校验前置；UI 滑块 min/max |
| 应用被强杀留下中间态 | 每个写操作独立可逆；RAII 守卫 |

## 验收标准
上述 6 项都有对应代码位置与（离线）测试证据；新增任何高频访问路径都要先算清"每秒多少次"。

## 证据要求
单测输出 + 频率计算（读次数 × 轮询频率）。

## 回滚方式
限速参数是常量，改回即可；串行化是结构性的，回退需整包回滚。

## 常见坑
- `get_status` 每轮读 13 个寄存器；20 ms 限速下 ≈260 ms/轮 —— 2 s 轮询安全，改成 200 ms 就会持续贴着上限
- **禁止**用 CPU/GPU 满载压测来"验证并发"（曾致本机无转储硬复位）
