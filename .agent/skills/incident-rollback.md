# Skill: 事故回滚（硬件 / 版本 / 合规）

## 适用场景
用户报告"设置乱了""档位不对""机器重启过""某版本有严重问题"。

## 前置读取
`docs/TROUBLESHOOTING.md`、`docs/SPEC.md` §5.1、`docs/DEPLOYMENT.md` §5、记忆 `ec-flooding-hardware-hazard`。

## 决策树
```
是否改动过 EC 寄存器？
├─ 是 → 应用内"撤销上次"（最近一次快照）
│        └─ 失败/无记录 → python -X utf8 -I tools/ec_mode_exp.py（脚本 finally 强制回滚）
│             └─ 仍异常 → 重启机器（EC 由 BIOS/固件复位初值）
└─ 否 → 机器重启发生在无操作时 → 跑 scripts/diagnose_reboot.ps1 取证
          （Event 41 / 6008 / 1001 / WHEA），按散热→BIOS→供电→内存顺序排查
是否代码问题？
└─ 是 → 回退到上一个 tag 的 exe（绿色免安装，无数据迁移）
```

## 验收标准
寄存器值回到事故前基线（用 `tools/ec_health.py` 核对 7 项关键值）；故障现象消失。

## 证据要求
事故前后寄存器读数、事件日志（若重启）、`git log`/`git tag` 指向的回退版本。

## 回滚方式
见决策树；**任何写入前必须先 snapshot**，失败要能自动回滚。

## 常见坑
- 撤销记录在 v0.1.0 里失败即丢；v0.1.1 起才"成功才出栈"
- 快照**不含** `0x0767`（自清零命令寄存器），别指望撤销它
- 看到"写入校验失败"是保护机制在工作，不是 bug —— 不要反复重试同一操作
