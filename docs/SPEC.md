# SPEC —— Mekrevo-Max 自研控制台

> 版本 1.0 · 2026-10-17
> 本文件是**编码前的规格基线**。任何功能改动都应先更新本文件，再动代码。

---

## 0. 这是什么

机械革命（MECHREVO）笔记本的**自研硬件控制台**，替代官方 ControlCenter3。

**交付形态**：Windows 桌面应用（Rust 核心库 + Tauri v2 界面）。
**运行前提**：管理员权限 + 已加载的内核驱动 `UWACPIDriver.sys`。

---

## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 成功标准 |
|---|---|---|
| G1 | 直接控制硬件，不依赖官方任何组件 | 只通过 `\\.\ACPIDriver` 内核驱动访问 EC |
| G2 | 关键操作可撤销 | 任何写入前存回滚点，失败自动回滚 |
| G3 | 失败必须可见 | 绝不把失败伪造成成功，绝不返回假数据 |
| G4 | 资源占用远低于官方 | 常驻内存 < 官方 178 MB 的 1/3 |
| G5 | 协议可验证 | 每个寄存器有实测证据与可信度标注 |
| G6 | 可持续演进 | 新机型/新功能可按本文档流程接入 |

### 1.2 明确的非目标（**重要：这些不做，是有意为之**）

| 不做 | 理由 |
|---|---|
| Web 服务 / HTTP API | 这是本地桌面硬件工具，没有服务端 |
| 数据库 / SQL / 缓存 | 无持久化数据层，配置用 JSON 文件即可 |
| 负载均衡 / CDN / 消息队列 / 分片 / 主从复制 | 单机单用户桌面应用，无此场景 |
| 多租户 / 鉴权 / 限流 | 本机管理员即唯一用户 |
| 高并发承载 | 见 §7 的并发定义（EC 访问竞争，非 QPS） |
| 云端部署 / 容器化 | 应用运行在用户自己的笔记本上 |

> **给评审者的说明**：如果需求方要求"Load Balancer / Redis / Kafka / 分片 / 限流"之类，
> 那是把桌面工具误当成 SaaS 了。本文档明确拒绝在不适用的场景堆砌基础设施。
> 真正对应的高可用诉求已映射为 §7 的"EC 访问健壮性"。

## 2. 用户与场景

**唯一用户**：本机管理员（笔记本机主本人）。

**核心场景**：
1. 我想知道现在风扇转多快、温度多少
2. 我想把性能档位从"均衡"切到"狂暴"打游戏
3. 我想让 CPU 功耗墙更激进/更保守
4. 我改错了，想一键撤销

**反场景**：远程访问、多人共用、无人值守后台服务。

## 4. 架构约束

```
┌─────────────────────────────────────────┐
│ app/  Tauri 桌面壳                       │
│   ui/      原生 HTML/CSS/JS             │
│   src-tauri/  IPC 命令层（薄）           │
└──────────────┬──────────────────────────┘
               │ 只依赖 core 的公开 API
┌──────────────▼──────────────────────────┐
│ core/  mechrevo-core（无 UI 依赖）       │
│   ec/        传输抽象 + Windows 实现     │
│   control/   功耗墙                      │
│   mode/      运行档位                    │
│   sensors/   只读传感器                  │
│   namespace/ 寄存器地址表（带可信度）    │
└──────────────┬──────────────────────────┘
               │ EcTransport trait（可替换）
┌──────────────▼──────────────────────────┐
│ \\.\ACPIDriver  →  UWACPIDriver.sys → EC│
└─────────────────────────────────────────┘
```

**硬约束**：
- C1 `core` 不得依赖任何 UI 框架或 Tauri
- C2 所有 EC 访问必须经过 `EcTransport` trait（保证可 Mock）
- C3 所有写入必须经过 `Ec::write_verified` 或显式说明为何不校验
- C4 寄存器地址必须标注 `AddrStatus`（Verified / CommunityUnverified / NotApplicable）
- C5 新增公开 API 必须有文档注释（`#![warn(missing_docs)]`）
- C6 限速与"不重叠"必须在**传输层**实现一次（`WindowsAcpiTransport::ioctl` + 进程级闸门），不得只写在调用层；只 sleep 不持锁不算实现
- C7 会写真实硬件的代码路径必须持有 `Ec::guard()` 返回的 `RestoreGuard`（保证 panic 也回滚）
- C8 IPC 命令名必须经前端 `IPC` 契约表调用，由 `ipc_contract.rs` 解析源码双向校验

## 5. 安全模型

| 风险 | 对策 |
|---|---|
| 写错寄存器损坏硬件 | 白名单地址 + 范围校验 + 写前快照 + 写后校验 + 失败自动回滚 |
| 用户误操作 | 高风险项（风扇曲线/电压/MUX）需单独确认；所有写操作可撤销 |
| 权限提升 | 不静默提权；权限不足时明确提示并由用户点击确认 |
| 官方驱动的"假成功" | 不信 `DeviceIoControl` 返回值，一律读回校验 |
| 敏感信息 | 不记录、不上传任何用户数据；无网络请求 |
| **EC 泛洪导致单片机停摆** | **强制限速：默认 ≤50 次/秒，硬上限 100 次/秒** |

### 5.1 ⚠️ EC 访问限速（硬性要求）

EC 是 8051 级单片机，**同时负责风扇控制与温控**。以数百次/秒泛洪 IOCTL 会让它停止响应：

```
EC 停摆 → 风扇/温控失控 → 平台硬复位（无 Windows 转储，Event 41 Kernel-Power）
```

**本项目开发过程中真实发生过一次这样的意外关机（2026-10-17）。**

规则：
- 所有 EC 访问工具**必须**限速，默认 ≤50 次/秒
- 代码中硬上限 = 100 次/秒，超出强制夹回，调用方无法绕过
  - Python 工具：`MIN_INTERVAL_S = 0.01`，在各自的 `Ec` 类内部强制执行
  - Rust 真机路径：`ec::AccessThrottle`，由 `WindowsAcpiTransport::ioctl()` 把**整个 IOCTL 过程**
    包进**进程级**闸门 `ec::throttle::global()` 内执行 —— 默认 20 ms（50 次/秒），
    硬下限 10 ms（100 次/秒）。同时保证：① 两次访问起点间隔达标；② 两次访问**不重叠**；
    ③ 新建 transport 实例无法绕过（状态进程共享）。见 `core/src/ec/throttle.rs`
- **禁止在笔记本上跑 CPU 满载压力测试**（同样会逼近温度墙导致硬复位）
- 本项目的"压测"定义为：长时**低速**轮询、写入/复原往复、设备掉线恢复、边界值拦截

### 5.2 无网络行为

本应用不联网（除可选的更新检查，需用户显式开启）。

## 6. 协议契约

### 6.1 EC 访问

| 项 | 值 |
|---|---|
| 设备 | `\\.\ACPIDriver` |
| 读 IOCTL | `0x9C40A488`（输入 4B 地址 → 输出 DWORD，取低字节） |
| 写 IOCTL | `0x9C40A48C`（输入 4B 地址 + 4B 值） |
| 打开方式 | `GENERIC_READ\|GENERIC_WRITE`，`FILE_SHARE_READ\|FILE_SHARE_WRITE` |

### 6.2 设备就绪前置（**官方漏掉的一步**）

```powershell
sc.exe start UWACPIDriver
pnputil.exe /scan-devices
```

### 6.3 已确认寄存器

见 `docs/protocol/ec-access.md`。摘要：

| 地址 | 含义 | 可信度 |
|---|---|---|
| `0x0740` | 项目 ID | Verified（读出 16，与官方一致） |
| `0x0730`–`0x0732` | Gaming 默认 PL1/2/4 | Verified（75/75/200） |
| `0x0734`–`0x0736` | Office 默认 PL1/2/4 | Verified（45/45/200） |
| `0x0464/0x0465` | CPU 风扇 RPM（大端） | Verified |
| `0x046C/0x046B` | GPU 风扇 RPM | Verified |
| `0x0751` | 档位字段 1（bit6=强冷） | Verified |
| `0x07AB` | 档位字段 2 | Verified |
| `0x0767` | 档位提交（自清零） | Verified |
| `0x0490` | 电源来源 | Verified |

## 7. "高并发/高可用"在本项目的真实含义

本项目**没有** QPS、没有连接池、没有多租户。真正需要扛的极端情况是：

| 真实场景 | 风险 | 对策要求 |
|---|---|---|
| EC 设备中途消失（驱动卸载/系统休眠） | 应用崩溃或显示错数据 | 每次访问失败要能被捕获并提示，不 panic |
| 多线程同时访问 EC | 数据错乱（EC 硬件通常不支持并发） | 访问必须串行化 |
| 轮询与用户操作同时发生 | UI 显示与硬件状态不一致 | 操作后强制刷新，轮询不得覆盖用户输入 |
| 驱动"假成功" | 用户以为改成功了其实没改 | 写后读回校验 |
| 极端值输入 | 硬件损坏 | 范围校验前置，写前拦截 |
| 应用被强制结束 | 硬件停留在中间状态 | 每个写操作独立可逆，不留中间态 |

**压力测试目标**（替代"并发压测"）：
- 连续 10000 次 EC 读，无失败、无句柄泄漏
- 100 轮"改档位→改回"，最终状态必须与初始完全一致
- 轮询 2 秒间隔连续运行 1 小时，内存无增长
- 设备中途拔除（停驱动），应用不崩溃且能恢复
