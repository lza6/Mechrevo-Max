## 5. 最强自我反驳与盲点扫描

> 这一节的作用是：在本指南被当成"待办清单"之前，先把它可能错的地方摆出来。

### 5.1 三个自我反驳

**反驳一：「v0.1.0 已发布、核心链路真机验证过，改进指南是过度工程。」**
部分成立。但事实是：**0 CI、0 覆盖率数据、0 安装包验证、0 证据入库、EC 访问未串行化、Rust 侧无限速护栏**（§1.3、§1.4）。版本号 0.1.0 与工程成熟度是匹配的，所以结论应当是**先补护栏，再加功能**，而不是"已经够好"或"推倒重来"。本指南 §7 的方案 B 正是这条路线。

**反驳二：「用户已经明确不要真机 E2E、要 mock 为主，那你提的很多任务都需要硬件，等于不可执行。」**
这条批评更锋利，也更接近真相。因此本指南**把所有 P0/P1 任务都设计成离线可验证**（串行化、限速装饰器、undo 不丢记录、测试回滚 guard、文档同步、CI）——它们全部能用 `MockTransport` 或纯逻辑测试证明。真正需要硬件的只有 §15 的 V-07（低频只读自检）与 V-08（低速 soak），且明确标注"需用户在场批准"。

**反驳三：「证据入库（P0-02）会不会违反合规红线？」**
需要精确区分：合规红线是**不分发官方二进制、驱动、反编译产物**（`docs/CONTRIBUTING.md:158-168`、`.gitignore:26-35`）。而"自研程序读到的寄存器基线"是可脱敏的协议事实（项目 ID=16、PL 值、档位编码）——**它们是自研结论，不是官方产物**。建议做法：提交一份**脱敏后的协议基线**（例如 `docs/protocol/ec-baseline.md` 内嵌 7 项关键地址表 + 扫描统计），而原始 `ec-scan.json` 继续不入库。这既补上证据链，又不越过红线。

## 6. 问题清单（分级 P0–P3）

> 每条都带 `file:line` 与判定方式。**P0/P1 是本指南的核心价值，P3 只记录不占交付时间。**

### P0 —— 阻塞交付（先修，再谈功能）

**P0-01 真机测试在断言失败时会把硬件留在改动状态**
- 位置：`core/tests/hardware.rs:106-133`（`real_write_then_restore`）、`core/tests/hardware.rs:135-172`（`mode_switch_roundtrip`）
- 事实（静态确认）：两个测试都是「写入 → 断言 → `change.undo()`」。Rust 没有 `finally`，一旦中间 `assert_eq!` panic，`undo()` **不会执行**，测试进程退出后寄存器停留在被改写的值。
- 对照：同类工具 `tools/ec_mode_exp.py` 用 `finally` 强制回滚（见 `docs/protocol/ec-access.md:139`），说明团队已知这个模式，只是 Rust 侧没做。
- 影响：这是唯一会**写真实硬件**的代码路径，且是"验证流程"本身。风险等级高于任何功能 bug。
- 修复方向：RAII guard（`struct RestoreOnDrop<'a,T>`，`Drop` 里无条件 `restore`），并让断言发生在 guard 生效之后；或在写操作前 `std::panic::catch_unwind` 兜底。**纯 Rust 逻辑，可用 Mock 单测验证 guard 行为**。

**P0-02 公开仓库没有可复核的证据链**
- 位置：`.gitignore:33-34`（排除 `reverse/evidence/*.json|txt`）；`git ls-files reverse/` 为空（V-06）；引用该路径的 5 处：`README.md:94`、`docs/protocol/ec-access.md:4,114`、`workflow_status.md:95`、`docs/CONTRIBUTING.md:165`、`docs/TROUBLESHOOTING.md:163`
- 事实：项目对外宣称的全部协议结论（项目 ID=16、Gaming 75/75/200、档位编码、风扇 RPM 组合方式）**在仓库内没有任何可查证材料**，只有文字。
- 影响：本项目立身之本是"真实验证、不伪实现"。第三方无法复核 = 可信度归零；同时违反"证据优先"原则。
- 修复方向（不越合规线）：新增 `docs/protocol/ec-baseline.md`，把**自研得出的、脱敏的**寄存器基线与扫描统计写进仓库（保留原始 json 不入库）；并在上述 5 处引用改为指向该文档。详见 §5.1 反驳三。

### P1 —— 高（主流程风险 / 硬性要求未落实）

**P1-01 EC 访问没有串行化，轮询与写入会重叠**
- 位置：`app/src-tauri/src/main.rs:24-28`（`AppState` 只有 `undo: Mutex`）、`main.rs:125-166`（`get_status` 每次新建 `Ec` 并读 13 个寄存器）、`main.rs:192-235`（写入路径同样新建 `Ec`）、`app/ui/app.js:410`（`setInterval(refresh, 2000)` 从不停歇）、`app/ui/app.js:81-83`（`setBusy` 只是改 `body.dataset.busy`，**不暂停轮询**）
- 事实（静态确认）：前端每次 `refresh()` 会 `invoke('get_status')`；`doSwitchMode` / `doApplyPower` 成功后又立刻 `await refresh()`。于是"定时轮询"与"动作后的刷新"可能同时在飞，各自打开独立句柄读写 EC。Rust 侧没有任何互斥。
- 违反：`docs/SPEC.md:209-213` 明确要求「多线程同时访问 EC → 访问必须串行化」。
- 修复方向：在 `AppState` 增加 `ec: Mutex<()>`（或更彻底：持有单个长生命周期的 `Ec` + `Mutex`），所有 EC 访问路径包在锁内；前端在 `busy` 期间暂停 `pollTimer`。**纯逻辑改动，可用 Mock 验证串行性与"轮询暂停"状态机**。

**P1-02 `undo_*` 失败时把回滚记录丢弃了**
- 位置：`main.rs:238-247`（`undo_power`：`undo.power.take()` 之后再 `record.undo(&ec)`，失败仅返回 Err）、`main.rs:250-259`（`undo_mode` 同构）
- 事实（静态确认）：`take()` 先出栈，若 `undo` 返回 `Err`，记录已被移出 `UndoStack`，用户**失去再次尝试撤销的机会**，而硬件可能处于"部分还原"状态（`restore` 逐个写，中途失败会留下部分已还原）。
- 修复方向：失败时把记录放回 `undo.power = Some(record)`；或 `restore` 返回已还原项数并支持重试剩余项。

**P1-03 Rust 侧完全没有 EC 限速护栏（安全硬性要求只落实在 Python 工具里）**
- 位置：`core/src/ec/mod.rs`（无任何节流）、`core/src/ec/windows.rs:112-145`（每读写一次都 `CreateFileW`/`CloseHandle`）
- 事实：`docs/SPEC.md:144-158` 要求「所有 EC 访问工具必须限速，硬上限 100 次/秒，代码内强制，调用方无法绕过」。Python 工具做到了（`tools/ec_scan.py:62-69`、`tools/ec_stress.py:51-60`、`tools/ec_health.py:57-60`），**唯一面向用户的 GUI 路径反而没有**。
- 当前风险量级：`get_status` 每轮约 13 次读 × 每 2 秒 ≈ 6.5 次/秒，**远低于阈值**（合理推断，未实测）。所以这不是"正在发生的事故"，而是"缺少护栏"：任何一次把 `POLL_MS` 改成 200ms、或加一个批量读功能，就会把应用推进危险区。
- 修复方向：`ThrottledTransport<T: EcTransport>` 装饰器（最小间隔可配，默认 20 ms = 50 次/秒，硬上限 10 ms），`Ec::new` 默认套上；单测可用假时钟或多个 `Instant` 断言间隔下限。

**P1-04 温度读数缺失（控制台类产品的核心信息）**
- 位置：`docs/SPEC.md:81`（列为 v0.2 首项）、`docs/VERIFICATION-LEDGER.md:138`（温度寄存器待验证）
- 事实：README 的"功能"与 UI 的三个读数卡（CPU 风扇 / GPU 风扇 / 供电）里**没有温度**（`app/ui/index.html:75-107`）。对目标用户（打游戏时想看机器热不热）来说，风扇 RPM 是代理指标，温度才是主指标。
- 修复方向：走"保守探测"——空闲态低速差分采样（限速 50 次/秒、全程只读），**不施加任何负载**（违反 SPEC §5.1 红线）；确认后按 §7 流程登记 `AddrStatus`。

**P1-05 文档过期已经发生（不是风险，是事实）**
- 位置：`docs/REQUIREMENTS-TRACEABILITY.md:23-24`（R10/R11 标未闭环，实际已完成）、`workflow_status.md:348-354`（"下一步"仍写 B1 待决策，实际已解决）、`CHANGELOG.md:48`（工具数 12 vs 实际 16）、`docs/VERIFICATION-LEDGER.md:103`（`ec_health.ps1` 不存在）
- 影响：这些文件正是"下一个人先读的东西"，过期等于误导。`docs/DEPLOYMENT.md:184-197` 的发布清单**没有一条检查文档一致性**，所以漂移无人拦截。
- 修复方向：修正上述 4 处 + 在发布清单加一条"运行 `docs/` 一致性自检"（可用简单脚本或人工核对表，见 T-11）。

## 7. 方案对比与推荐

### 7.1 候选方案（4 个）

**方案 A：广度优先 —— 快速铺满功能**
按官方能力表（`workflow_status.md:144-163`）逐项补齐：温度、键盘背光、电池充电上限、风扇曲线、MUX、超频。优点是最快缩短与官方控制台的功能差距，用户在界面上"看到东西变多"；缺点是这些新功能里**大半需要新的寄存器逆向**（B-01：每机型都要重来），且风扇曲线/电压/MUX 属高风险写操作，一次写错可能导致风扇不转或机器无法启动。更关键的是，它**不解决任何 P0/P1**——在证据链断裂、无 CI、EC 未串行化的地基上加功能，等于把风险面积扩大。

**方案 B：护栏优先 —— 先让"可信、可复现、安全"成立**
不新增任何硬件功能，只做六件事：串行化 EC 访问、加 Rust 侧限速装饰器、修 undo 记录丢失、给真机测试加 RAII 回滚 guard、把脱敏协议基线纳入仓库补上证据链、建 CI 拦文档漂移。全部可在**无硬件、无网络、无权限**的条件下用 Mock 与静态检查验证，零硬件风险，完全符合"以 mock 为主、不做真机 E2E"的既有指示。缺点是短期内界面上"什么都看不出变化"，对想看到新功能的期待是反直觉的。

**方案 C：产品化优先 —— 做成小白能装能用的东西**
补齐安装包（msi/nsis）、托盘常驻、开机自启、自动更新（需签名）、首次使用向导（一键 `sc start` + `pnputil /scan-devices`，解决 B-05）、多级撤销与"恢复出厂"（B-07）、错误文案人性化。优点是直接解决"官方控制台一堆 bug、我们的能不能真的替代"这个用户视角的核心问题；缺点是自动更新需要代码签名密钥与托管方案（当前没有），且托盘/自启会引入新的常驻与权限问题，需要真机验证——与"不做真机 E2E"冲突最大。

**方案 D：平台化优先 —— 先把多机型抽象做出来**
把寄存器定义从 Rust 常量表外置为数据（`toml`/`json` + 机型档案），引入能力协商（读 `ProjectID`/BIOS 标识后选择档案），`AddrStatus` 从编译期常量升级为运行期能力查询。优点是直击 B-01 这个长期成本黑洞，为社区贡献机型档案打开入口（这正是开源项目最需要的杠杆）；缺点是需要至少 2 台不同机型才能验证抽象是否成立——**当前只有 1 台**，属于"没有证据支撑的设计"，容易做出错误的抽象（YAGNI）。

### 7.2 权衡矩阵（1 = 最差，5 = 最好）

| 维度 | A 广度 | B 护栏 | C 产品化 | D 平台化 |
|---|---|---|---|---|
| 解决当前 P0/P1 | 1 | **5** | 2 | 3 |
| 无需硬件即可验证 | 2 | **5** | 2 | 4 |
| 对用户的可见价值 | 4 | 2 | **5** | 2 |
| 长期维护成本收益 | 2 | 4 | 3 | **5** |
| 风险（高=危险） | 🔴 高 | 🟢 低 | 🟡 中 | 🟡 中 |
| 与既有安全策略相容 | 2 | **5** | 3 | 4 |
| 与当前证据量匹配 | 2 | **5** | 3 | **1**（只有 1 台机器） |
| 可衍生性（为后续铺路） | 3 | **4** | 3 | **5** |

### 7.3 推荐：**B 优先 → A 的最小可信子集 → D → C**（顺序执行，不并行）

理由（按证据）：

1. **B 的每一项都对应一条已确认的 P0/P1**（P0-01、P0-02、P1-01、P1-02、P1-03、P1-05），不是"最佳实践洗脑"。
2. **B 全部零硬件风险**，完全在用户划定的"mock 为主"边界内可闭环——这是唯一能立刻全面验证的方案。
3. **A 只取"只读"子集做第一步**：温度读取（P1-04）是唯一既高用户价值、又不写硬件的功能。风扇曲线等写操作必须等 B 完成后再单独立项（`docs/ARCHITECTURE.md:195-199` 的风险分级已明确要求）。
4. **D 必须等第二台机器**，否则是凭 1 个样本做抽象——明确推后，而不是放弃。
5. **C 的自动更新需签名密钥**，属"需用户确认后执行"的外部件（`docs/DEPLOYMENT.md:140` 只说方案未定），排在 D 之后。

**何时推翻这个推荐**：如果用户的真实目标是"尽快能在别人的机械革命上装起来用"，则 C 的"首次使用向导 + 安装包 + 恢复出厂"应提到 B 之后立刻做。

> **2026-10-24 更新（已拍板，见 §17）**：用户选择 **A 的最小只读子集（温度读数）作为 v0.1.1 之后的下一站**，因此执行顺序为 **B（v0.1.1）→ A-只读（v0.2.0）→ 工程化（v0.2.1）→ D（v0.3.0，仍 blocked 于第二台机器）→ C（v0.4.0）**，C 不再提前。

## 13. 风险登记与回滚

| 风险 | 触发条件 | 影响 | 缓解 | 回滚 |
|---|---|---|---|---|

| 文档再次漂移 | 改代码不改文档 | 误导下一个人 | CI + 发布清单新增检查 | 修正并回填台账 |
| 自动更新被投毒 | 未签名更新 | 供应链风险 | v0.4 之前不实现；实现时必须签名 + HTTPS | 立即下线更新源 |

## 19. T-040-04 风扇曲线写入 · 高风险评审方案（2026-10-25，Q-06=(b) 拍板后）

> **状态：评审文档，未获用户对方案本身的批准前不写实现代码。**
> 用户已拍板直接进本方向；真机 E2E 已恢复为合法验证手段（Q-07 策略纠正），但本节的硬件级安全约束（限速、回滚、用户在场）不因 E2E 解禁而放松——它们防的是 EC 泛洪手法与过热事故，与验证方式是两回事。

### 19.1 现有事实（已验证，不重复调查）

| 事实 | 证据 |
|---|---|
| EC `0x0F00–0x0F5F` 六个 16 字节块：2 组「温度点表 + 占空比表」（CPU: 0x0F00/0x0F20，GPU: 0x0F30/0x0F50；0x0F10/0x0F40 为带序号头的变体） | `fancurve.rs` seed 与 2026-10-24 真机扫描一致 |
| 占空比实际值集中在 192/196/200（≈75-78%），说明默认曲线是**窄带稳速曲线**，非 0-255 全范围 | 同上 |
| 官方 profile 只有表名 `M1T1`，曲线本体在 `UserFanTables/PH6PG*` 资源，**本机备份中没有** | `CHANGELOG.md`、`ec-baseline.md` §6 |
| `Ec::write_verified`（写→读回校验）、`RestoreGuard`（panic 安全回滚）、进程级限速闸门（≤50 次/秒）均已存在并被单测覆盖 | `core/src/ec/mod.rs:117`、`throttle.rs` |
| 提交寄存器类"写后自动清零"模式在本项目已知（`0x767`），风扇表写入**可能**存在类似触发，未证实 | `mode.rs` 注释 |
| RPM 读数：CPU `0x0464/0x0465`、GPU `0x046C/0x046B`，已交叉核对 | `ec-baseline.md` §3 |

### 19.2 风险模型（为什么这是 🔴）

1. **写入非法曲线 → 风扇停转 → 过热**：占空比写 0 或表结构破坏，风扇可能按 0% 运转。温度读数存在（0x043E/0x044F）且轮询在线，可做**停转检测**，但 EC 停转不一定立刻反映 RPM。
2. **表配对未经交叉核对**：温度点表与占空比表的配对是**数据特征推断**（`pair_points` 自注释"不是协议结论"）。写错配对 = 把 GPU 曲线写进 CPU。
3. **可能的隐藏触发/索引寄存器**：官方表格名 `M1T1` 暗示存在表选择机制；直接写 0x0F00 区可能不被固件采纳（写了不生效，伪成功）或被某索引寄存器间接寻址。
4. **0xFF 填充语义不明**：填充是"无效点"还是"保留"？把 0xFF 写成有效值可能扩大激活区。

### 19.3 三种实现方案对比

| 维度 | 方案 1：整表快照+原子写回（传统） | 方案 2：逐格写+读回+停转监视（推荐） | 方案 3：只做"恢复出厂"不做自定义（保守） |
|---|---|---|---|
| 做法 | 一次 snapshot 96 字节 → 用户提交整条新曲线 → 逐格 write_verified → 任一失败整表回滚 | 每格 write_verified 后读回；写入期间后台每 2s 读 RPM，任一风扇 RPM→0 立即整表回滚 + UI 告警；写入成功后 60s 观察窗内持续监视 | 只实现"一键恢复出厂曲线"（snapshot 存档→写回原值），不做自定义编辑 |
| 用户价值 | 高 | 高 + 最安全 | 低（只兜底，不能调曲线） |
| 开发成本 | 中 | 中高（+监视任务、UI 告警态） | 低 |
| 风险 | 中：写入中途失败回滚窗口内风扇状态未知 | 低：停转即回滚，观察窗捕获迟发效应 | 极低 |
| 与现有护栏契合 | 复用 write_verified + RestoreGuard | 完全复用 + 新增监视接缝 | 完全复用 |
| 结论 | 否——中途失败窗口不可接受 | **推荐** | 作为方案 2 的**组成部分**保留（出厂曲线一键恢复） |

**决策：采用方案 2，并把方案 3 的"恢复出厂"作为其内置功能。** 理由：奥卡姆剃刀不适用于安全场景——这里多一层监视不是过度设计，是把"写错→过热"的后果窗口压到最小。

### 19.4 定案的技术规格（评审通过后按此实现）

1. **前置核对（硬件阶段第 1 步，只读）**：真机重扫 0x0F00–0x0F5F 并与 2026-10-24 基线逐字节比对；切换游戏档/办公档再读，确认曲线表是否随档位切换（若随档切，说明存在档位→表映射，直接写会冲突）。工具：`tools/ec_health.py` 扩展或新增 `tools/ec_fan_dump.py`（只读、限速）。
2. **表配对确证**：修改单格占空比（如 0x0F20 第一格 192→190，仍在安全带内且 CPU 高转速侧），观察 RPM 是否响应变化——这是配对正确性的**行为级证据**。不响应则配对错误，停止。
3. **写入原语**：逐格 `write_verified`；**禁止**整块一次性写（本项目无块写 IOCTL，天然逐格）。
4. **停转监视**：写入会话期间独立任务每 2s 读两组 RPM（复用现有采样路径，不新增 IOCTL 频率负担——RPM 本就在 2s 轮询里）；RPM 低于写入前基线的 30% 即回滚。
5. **回滚**：写入前 snapshot 全部 6 块；失败/超时/停转 → 按地址升序逐格回写快照 + `RestoreGuard` 兜底 panic；回滚本身也 write_verified。
6. **用户在场约束**：所有真机写入会话需用户明确批准窗口；UI 写入按钮二次确认（复用 T-052 的确认模式）；确认文案明示"写入期间风扇行为将临时改变"。
7. **恢复出厂**：首启动或写入前自动 snapshot 存档到应用数据目录（含 SHA256 校验），"恢复出厂曲线"用存档写回。
8. **不改**：`AccessThrottle`、`Ec` 原语、`RestoreGuard`、轮询频率——全部复用。
