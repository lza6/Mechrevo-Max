1. 上下文：为什么这次不发新功能

v0.1.0 已经在真机上跑通读数、档位切换、功耗墙写入，功能上"能用"。但一次只读复审发现，三个最关键的信任基础是空的：

  • 证据链断裂：README / 协议文档 / 台账 5 处指向 reverse/evidence/，而 git ls-files reverse/ 输出为空 —— 公开仓库里没有任何可复核材料。
  • 安全护栏只落在 Python 工具里：docs/SPEC.md §5.1 要求"所有 EC 访问必须限速"，唯一面向用户的 GUI 路径（Rust）却一行限速都没有。
  • 验证流程自身有洞：真机测试"写入 → 断言 → 回滚"，Rust 没有 finally，断言一失败回滚就被跳过，硬件留在改动后的状态。

在一个"立身之本是真实可验证"的项目里，这三点比缺温度读数严重得多。所以 v0.1.1 只做护栏，不加功能。

安全与正确性

  • AccessThrottle（新）：任意两次 EC 访问间隔 ≥ 20 ms（50 次/秒），请求低于 10 ms 被强制夹回。挂在 ioctl() 首行，新增路径也无法绕过。
  • RestoreGuard（新）：RAII 回滚守卫，Drop 里执行 restore；catch_unwind 单测证明 panic 路径也会还原。
  • AppState.ec 互斥：所有 IPC 命令持有同一把锁，lock_ec_serializes_access 断言临界区内并发者恒为 1。
  • undo_* 改为"撤销成功才出栈"，失败时保留回滚点。
  • 锁中毒不再 panic：返回 hint: "restart"，前端显示"需要重启程序"并给一键重启按钮。
  • 0x0767（自清零提交寄存器）移出快照集合 —— 撤销时不再去写一个语义未定义的命令寄存器。

证据链与工程

  • docs/protocol/ec-baseline.md（新）：7 项交叉核对地址 + 传感器/档位编码 + 全量扫描统计（4096 地址 / 2002 非零 / ≈6.6 s）+ 复现命令 + 未验证清单；原始 JSON 继续不入库。
  • 前端 IPC 契约表 + 契约测试解析源码，双向比对；并断言源码里不存在直接传字符串命令名的 invoke。

  • 删两个空目录（protocol/、test/），graft/ 进 .gitignore。
  • 修正 4 处文档过期（需求矩阵 R10/R11、workflow_status 的"下一步"、工具数 12→16、不存在的 ec_health.ps1），发布清单新增"文档一致性自检"。

8. 测验（自测：100%，18/18 项）

规则：选择题/判断题每题 6 分，简答题按要点计分；通过线 80%。下方可展开答案。

一、选择题

  1. 限速为什么放在 WindowsAcpiTransport::ioctl() 而不是调用层？
    答案

    因为它是唯一的真实硬件出口；放在调用层的话，任何新增路径（或直接用 Ec::new）都能绕过，护栏就退化成建议。

  2. 0x0767 为什么既不做读回校验、也不进快照？
    答案

    它写入后由固件自动清零：读回必然不一致（会误报写入失败）；同时它没有"原始值"可言，撤销时去写它等于发出一次语义未定义的命令。

  3. 撤销功耗改动失败后，为什么记录要保留？
    答案

    restore 是逐个地址写、中途失败会留下部分已还原的状态；保留记录才能重试收尾。原实现 take() 后失败 → 记录永久丢失，用户再无手段。

  4. 契约测试为什么改成解析 app.js 源码？
    答案

    原来的两张手写表互相比较，前端新增一个 invoke 而忘记同步表时测试依然是绿的；解析源码才能发现"前端调了后端没有的命令"。

  5. 为什么 cargo test --test ipc_contract 通过不代表命令层没问题？
    答案

    该测试目标不编译 main.rs（bin 目标）。必须另跑 cargo check --all-targets 或 cargo test --bin mechrevo-max。

二、判断题

  1. "DeviceIoControl 返回 TRUE" 足以证明硬件执行成功。
    答案

    错。官方驱动存在把失败改成成功的路径；本项目一律写后读回校验。

  2. 守卫 RestoreGuard 在断言 panic 时也会回滚。
    答案

    对。panic 展开会执行 Drop；guard_restores_after_panic 用 catch_unwind 验证。

  3. 锁中毒时 get_status 应该 panic，让用户重启。
    答案

    错。应返回结构化状态 + hint:"restart"，panic 只会让 UI 永久卡死。

  4. 脱敏协议基线文档可以包含原始 4096 地址扫描 JSON。
    答案

    错。原始数据含本机特征值，按合规红线不入库；只入库地址表、统计与交叉核对来源。

  5. 忙时暂停轮询纯粹是为了省电。
    答案

    错。主要是避免写入期间并发读造成读数抖动、无谓排队与状态错位。

三、简答题

  1. 用三句话说清"为什么 v0.1.1 不加新功能"。
    答案要点

    ① 证据链断裂、限速缺失、验证流程自身有洞，三个 P0/P1 直接侵蚀"可验证"这个卖点；② 这些全部能离线验证，零硬件风险，符合"mock 为主、不做真机 E2E"的既定策略；③ 在断裂的地基上加功能只会扩大风险面。

  2. 如果用户报告"设了功耗墙，重启后又变回去了"，你怎么排查？
    答案要点

    ① 本应用不写持久化配置，改动只在 EC 寄存器，初值由 EC/BIOS 决定（先说明这是已知限制，非 bug）；② 用 tools/ec_health.py 核对当前值与基线；③ 确认是否被官方控制台或 BIOS profile 覆盖；④ 如果用户期望"保持"，那是一个功能需求（v0.2.0 的多级撤销/恢复出厂 + 文案说明）。

  3. 要在 v0.2.0 加温度读数，第一步必须做什么？为什么？
    答案要点

    先确认寄存器：空闲态、低速只读（≤50 次/秒）、不施加任何 CPU/GPU 负载、用户在场，并与外部工具交叉核对；未核对前 AddrStatus 只能标 CommunityUnverified 且禁止任何写入引用。因为跨机型地址不通用（社区称 0x0783 是当前 PL，本机恒为 0）。

  4. 回滚这次版本的两条独立路径分别是什么？
    答案要点

    ① 软件：下载 v0.1.0 的绿色单文件 exe 覆盖（无安装、无数据迁移）；② 硬件：应用内撤销 → tools/ec_mode_exp.py（finally 强制回滚）→ 重启机器由 EC/BIOS 复位初值。

9. 独立复审（v0.1.2）：两次声明只成立一半

初版发布后，我启动了一个只读的独立审查代理（不继承我的推理）。它给出 CONDITIONAL PASS， 并指出 v0.1.1 最核心的两条保证其实不成立 —— 这两条都已被它实测确认，不是猜测：

编号它指出的问题为什么是硬伤修复
R1（P1） AccessThrottle::wait() 在返回时就释放了锁，真正的 DeviceIoControl 在锁外执行 只约束了"两次访问的起点间隔"。若单次 IOCTL 本身慢于 20 ms（EC 慢响应、驱动阻塞都属正常），两次访问照样重叠 —— 正是 SPEC §5.1 要禁止的状态。配套测试只断言总耗时，发现不了重叠 run(closure)：整个访问（open + IOCTL + close）持锁；间隔从上次结束计时
R2（P1） 闸门是 WindowsAcpiTransport 的字段，而每条 IPC 命令都 new() 一个 transport 每 new() 一次就得到一份空状态 → 每条命令的第一次访问零间隔；未来任何新路径（CLI、脚本、新命令模块）建个 transport 就绕过了。"不可绕过"只在单实例内成立 进程级单例 ec::throttle::global()（OnceLock），全进程共享
R3（P2） 证据台账把 clippy/fmt 记成无条件通过，实际只跑过 core app 的 fmt --check 实测失败（9 处），clippy 有 3 个警告 —— 台账断言超出实际范围 修掉 3 个 lint（manual_clamp×2、err().expect()×1）+ 全量 fmt；台账标注 scope
R4（P2） mode.rs 新注释称"撤销时再写一次提交触发即可"，但 undo 并不写 0x767 注释与实现互斥，下一个人会照着注释做错事 注释与实现对齐，并标注"撤销后固件是否立即重新应用尚未在真机确认"
关键收获：这四条我自己审不出来。R1/R2 的错误来自同一个思维惯性 —— "我把限速放进了传输层，所以调用方绕不过"，而事实上"放进传输层"和"覆盖整个访问"、"进程级共享"是三件事。 自审会沿用同一套假设，独立复审的价值就在这里。因此它被写进了 AGENTS.md 的审查门禁： 每个版本必须有一次不继承实现者结论的独立审查。
